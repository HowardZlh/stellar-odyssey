> 中文原版 / Chinese original: [../how-it-works.md](../how-it-works.md)

> technical problems in plain language.

## 1. How does one scene span 10+ orders of magnitude?

From a close-up of Earth (camera a few thousand kilometers away) to the edge of the
observable universe (46.5 billion light-years), spatial scale spans more than 10 orders
of magnitude. A single-precision floating-point depth buffer breaks down completely at
this range (z-fighting flickers across the whole screen).

The combination of fixes:

- **Logarithmic depth buffer**: the Three.js renderer enables `logarithmicDepthBuffer`,
  distributing depth precision logarithmically so both the near field and the extreme
  far field stay stable;
- **Continuous level interpolation**: the scroll wheel drives a continuous quantity
  `continuousLevel` (1.0–4.0), and the content of the four view levels
  (planet / solar system / galaxy / universe) cross-fades according to it — not a
  "scene switch", but the opacity/mount state of each layer's content within the same
  scene graph transitioning smoothly with zoom;
- **Log-interpolated time compression**: planetary rotation (hours) and galactic
  evolution (hundreds of millions of years) differ by a dozen-plus orders of magnitude
  in time scale, so each level has its own time-compression ratio, interpolated
  logarithmically across levels — the flow of time never jumps while zooming;
- **Scale-ruler synchronization**: the HUD ruler unit (AU / light-year / Mpc) shifts
  automatically with zoom, driven by a unified scale-management pure function
  (`src/utils/scale.ts`).

## 2. Why are the planets "exactly where they should be today"?

The solar system is not artistic placement but real orbital mechanics:

- Each planet uses NASA JPL's **six Keplerian orbital elements** (semi-major axis /
  eccentricity / inclination / longitude of ascending node / argument of perihelion /
  mean anomaly, J2000 epoch);
- Every frame solves **Kepler's equation** `M = E - e·sin E` (Newton iteration) to get
  the true position from the mean anomaly — Kepler's second law comes for free (fast at
  perihelion, slow at aphelion);
- On launch, the initial phase is computed from the real current date, so the planetary
  positions you see match tonight's astronomy software;
- Every particle in the asteroid belt / Kuiper belt has its own independent Keplerian
  parameters, advanced in the **vertex shader** — 40,000+ particles at zero CPU cost,
  with the "Keplerian shear" (inner ring fast, outer ring slow) emerging naturally.

Implementation: `src/utils/physics.ts` (with full unit tests).

## 3. Volumetric nebulae: raymarched emission–absorption integration

The Orion Nebula is not a texture; it is genuine **volume rendering**:

- The nebula density field is baked into a **3D texture** (≤128 per dimension);
  procedural primitives (ellipsoidal shells / cavities / filamentary perturbations)
  compose the real hallmark features — the scalloped emission cavity, the dark bay
  silhouette — with the right relative orientation and magnitude;
- The fragment shader **raymarches** along the view ray (up to 64 steps), progressively
  accumulating the emission–absorption integral (Beer–Lambert extinction + emission
  term), with a two-color split of Hα red / OIII teal;
- **Blue-noise dithering** scatters the step start points, trading banding artifacts
  for perceptually uniform noise;
- **Half-resolution render target**: the volumetric layer is first rendered to a
  1/2-resolution RT and then upsampled and composited — half the cost with almost no
  visible loss;
- **FPS-adaptive quality tiers**: when the 3-second sliding-window FPS drops below
  threshold, step count (64→32) and RT resolution are reduced automatically, and
  restored once performance recovers — low-end devices degrade smoothly instead of
  dropping frames (`src/utils/adaptiveQuality.ts`).

## 4. Black-hole gravitational lensing: how the photon ring gets bent

The imagery when zooming in on Sagittarius A* (Sgr A*) is generated by a dedicated shader:

- A **screen-space approximation of light deflection** modeled on ray bending under the
  Schwarzschild metric: the background star field is warped in inverse proportion to
  the distance from the black hole's projected center — the closer, the stronger the
  bending — producing the Einstein-ring-like drag;
- **Photon ring**: the brightened annulus near the critical radius where light wraps
  around multiple times;
- **Accretion disk**: temperature is mapped to color by radius via the blackbody
  spectrum (hot inside, cool outside), overlaid with **Doppler beaming** (the side
  approaching the observer brightened and blueshifted, the receding side dimmed and
  redshifted) and **gravitational redshift** — precisely the physics behind the
  "bright top, dark bottom" of the EHT photo;
- M87* reproduces the EHT 2019 morphology: disk inclination 17°, nearly face-on,
  triggered by the follow zoom-in.

The formulas inside the shader have **CPU mirror functions** in `src/utils/` with unit
tests asserting the GPU and CPU sides share the same constants — even rendering code
can be anchored by tests.

## 5. Where the real data comes from: the offline baking pipeline

**Zero external network requests** at runtime, yet the data is all real — the secret is
build time:

```
Gaia DR3 (TAP/ADQL) ──┐
SIMBAD ───────────────┤   scripts/bake-data/          public/data/
2MRS catalog (VizieR) ─┼──> fetch→validate→bake ─────> static artifacts ≈2.5 MB
DSS2 imagery (hips2fits) ─┘   (idempotent, artifacts committed to the repo)      (shipped with the app)
```

- **Pleiades**: 600 genuine member stars selected from Gaia DR3 by parallax + common
  proper motion; 3D positions / magnitudes / colors are all real;
- **Cosmic background**: a 3D point cloud of 43,488 galaxies from the 2MASS Redshift
  Survey, with redshift converted to distance via the Hubble flow — the Virgo cluster
  concentration and the zone of avoidance are the shape of the data itself, and the
  entire catalog costs just **2 draw calls** (a single BufferGeometry + vertex shader);
- **Galaxy close-ups**: DSS2 color imagery of M31/M33 and the Large/Small Magellanic
  Clouds is baked into three weight maps — density / color / dust — and M31 is
  **deprojected back onto its disk plane** at its true 77° inclination; at runtime the
  particle cloud is distributed by sampling these maps, so the spiral arms and dark
  dust lanes match the real photographs feature for feature;
- Every artifact self-validates (value ranges / counts / scientific sanity) before
  being written, and the meta records the source, license, and retrieval query;
  if loading fails at runtime, it automatically falls back to the procedural path.

## 6. Performance: how 60 FPS is defended

| Technique | Description |
|---|---|
| Zero allocations in the render loop | No `new` objects inside `useFrame`; Vector3 etc. are all pre-allocated and reused; GC hitches eliminated |
| Registry pattern bypassing React | Per-frame pose data is written into a registry by a single writer; rendering and camera resolution consume it directly — no React state, zero re-renders |
| Particles in the vertex shader | The 43,000 galactic-disk particles, belt asteroids, and the 2MRS point cloud are all advanced on the GPU |
| Detail-layer LRU pools | Heavy assets like black-hole lensing / volumetric nebulae / galaxy close-up particles lazy-mount on "follow + distance threshold"; four resource pools, capacity 1 each, eviction disposes immediately — GPU memory is fully accounted for (`src/hooks/useDetailLayer.ts`) |
| Labels mutate the DOM directly | Body labels change their transform directly each frame without triggering React renders |
| Transparent-layer order registry | The renderOrder of all L4 transparent layers is registered centrally (`src/utils/universeRenderOrder.ts`), eliminating inter-frame flicker from crossed depth sorting |
| FPS adaptation | See the volume-rendering quality tiers above |

Measured: during a long L4 tour the JS heap stabilizes at ~50 MB after GC, and 60 FPS
never drops.

## 7. How a 3D app reaches 3,000+ unit tests

The principle is **pure functions first**: all computable logic (orbit solving, scale
conversion, event-scope gating, animation curves, quality-tier decisions, the kiosk
mode state machine) is written first as pure functions in `src/utils/` with unit tests,
and components only do wiring. As a result:

- Physical correctness can be asserted (orbital-parameter ranges, Keplerian conservation);
- Shader formulas are anchored by CPU mirror functions;
- Kiosk mode is a pure state machine (`src/utils/kiosk.ts`, 100% coverage) whose three
  state transitions are all enumerable in tests;
- The coverage gate ≥90% is enforced by the jest config; CI fails below threshold.

UI/rendering changes additionally go through **visual verification in headless
Chrome**: CDP drives key presses / DOM assertions / screenshot comparison, and dev
hooks expose the store and the GPU-memory ledger for scripted assertions
(see [development.md](development.md)).
